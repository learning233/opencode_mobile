# 会话历史缓存（SWR 秒开）

实现日期：2026-08-30。改动子系统前先读本文。

## 1. 背景与目标

设备端实测打点：打开历史会话 4.45s 中 99.5%（4428ms）耗在网络请求与服务端大 JSON 传输，客户端解析（14ms）与状态分配（7ms）可忽略。为此引入 **SWR（Stale-While-Revalidate）本地缓存**：先出本地缓存立即渲染，后台网络静默对齐，目标把历史会话打开耗时从 ~4.4s 降到几十 ms 量级。

## 2. 数据流总览

```
用户打开/切换会话 (loadMessages)
     │
     ├─ [阶段1] 内存 messages 为空 → 读本地缓存 (~5-20ms) → 立即渲染（秒开）
     │
     └─ [阶段2] GET /session/:id/message 照常发出（串行在缓存读取之后）
                │
                ├─ 快照未过期 → assignAll 对齐 + 异步落盘
                └─ 快照已过期（生成中/发送在途）→ 跳过赋值与落盘
     │
回合收尾 (session.idle / session.error / abort)
     └─ [阶段3] _finalizeStreamingText 对齐后 → 内存快照落盘（Sync-on-Idle）
```

## 3. 存储格式与位置

- 引擎：`lib/utils/session_cache_store.dart`（`SessionCacheStore`，普通单例 + 可注入 `baseDir`，未注册 GetX）。
- 路径：`getApplicationSupportDirectory()/session_cache/<sessionId>.json`（项目惯例：support 目录放缓存，参照 `image_cache.dart`）。
- 文件内容：`{"v":1,"messages":[...]}`。`messages` 为**时间正序、已过滤 `isChatMessage`** 的服务端原始 JSON（即 `MessageModel.raw`）。归一化在**写入侧**完成，读取侧直接 `MessageModel.fromJson`，两条路径渲染结果必然一致（归一化逻辑抽为 `SessionController.normalizeServerMessages`，网络路径与测试共用）。
- 空列表不落盘且清理旧快照：空会话宁可无缓存、走正常网络加载态。当 `save(sessionId, [])` 保存空消息列表时，主动调用 `delete(sessionId)` 清理磁盘旧快照，防止被清空或重置的会话在冷启动后旧消息"幽灵复活"。

## 4. 关键设计与守卫

### 4.1 秒开读取（`loadMessages` 内）

- 位置在 `historyLoadFailed/hasLoadedHistory` 重置行**之后**：先重置再读缓存，缓存命中置 `hasLoadedHistory=true` 才不会被重置覆盖。
- 仅当 `messages.isEmpty` 才尝试：SSE 预填充、重连强刷场景消息非空，自然跳过走原路径。
- **串行读取**（先 await 缓存、后发 GET）：天然规避"缓存后到覆盖新数据"的乱序竞态，代价是 GET 晚 5–20ms 起跑。不要改成两者并行——并行需要额外的"网络已着陆则丢弃缓存结果"标志，收益不足。
- 读取后先查 `seq != _sessionFetchSeq`（防切项目竞态：`stateOf` 会为新项目凭空建状态，污染新项目内存）。
- **健壮性与异常降级**：读取与反序列化包裹 `try-catch`。文件缺失、版本不符、损坏或反序列化失败一律静默降级走网络，若损坏自动调用 `delete(sessionId)` 移除脏文件，彻底避免前端卡死全屏 Loading。
- **秒开即同步模型**：缓存命中后立即调用 `_syncModelFromHistory`，从历史记录恢复最近使用的模型与思考档位，确保秒开后即可用正确模型开始交互，无需等待网络往返。

### 4.2 revalidate 对齐守卫

网络成功分支内，仅 **assignAll + `streamingPartText.clear()` + 落盘** 三步被守卫：

```dart
final snapshotStale = !force && !flaggedReload &&
    (state.isGenerating.value ||
        _localSendInFlight.contains(sessionId) ||
        state.streamingPartText.isNotEmpty);
```

- 守卫条件**不能只看 `isGenerating`**：stale 结束事件会误复位生成态（见 `session_controller.dart:87` `_localSendInFlight` 的注释），4.4s 的 SWR 窗口内极易撞上，所以加上 `_localSendInFlight` 与流式通道非空两条。
- **`force || flaggedReload`（重连强刷）豁免守卫**：全量历史是权威数据，生成中也必须落快照纠正断线残留（`_refreshAfterReconnect` 对生成中的活跃页签强制 `loadMessages(force: true)`）。
- **守卫只跳过赋值/清通道/落盘**，model 选择同步、`_markStaleQuestionsSkipped`、reconcile 等副作用保持无条件执行——它们 today 不依赖赋值结果，整块 early-return 会弄坏问题恢复。

### 4.3 回合收尾落盘（Sync-on-Idle）与 Revert 状态闭环

`_persistSessionCacheSnapshot` 把内存消息快照落盘，调用点必须都在 `_finalizeStreamingText` **之后**（晚到 delta 在 idle 之后仍可能到达，finalize 前落盘会缺尾部内容）：

| 调用点 | 位置 |
|---|---|
| `_onSessionIdle` 末尾（队列 flush 前） | `_onSessionIdle` 监听处理 |
| `_onSessionError` 两个正常收尾分支 | 错误终止分支 |
| `abortGeneration` 状态复位后（保留部分生成内容） | `abortGeneration` 内部 |

- **落盘守卫**：消息为空、生成中、本地发送在途、流式通道未清空、**`revertMessageID` 非空** 时跳过落盘。revert 只隐藏不截断内存消息，照存会把已撤销的消息带进缓存；跳过后缓存保留上一次网络快照，由下次 revalidate 自愈。
- **`revertMessageID` 状态闭环**：服务端在 `revert` 发生时记录回退点；在 `fetchSessions` 与 `_onSessionUpdated` 中同步恢复。当会话继续推进使得服务端 `revert` 变空时，客户端同步将已存在的 `revertMessageID.value` 置空，防止 `chat_view` 误截断新消息。

### 4.4 缓存引擎内部

- 编解码走 `compute` 隔离线程（大会话数 MB，避免主线程卡帧）。
- 原子写：写 `.tmp` → rename 覆盖，失败清理 tmp，断电/闪退不留半截文件。
- 写入串行队列：save/delete/clearAll/prune 共用一条 Future 链，防同一文件 tmp+rename 交错，也防 delete 后被先入队的 save 重新写出已删会话的文件。
- **LRU 淘汰优化**：淘汰检查与执行从读路径（`load`）剥离，移入写队列（首次写入 `save`）中执行，读操作直达文件零额外 I/O；文件数 > 200 或总量 > 64MB 按 mtime 从旧到新删；扫描时自动清理意外残留的 `.tmp` 文件。
- sessionId 直接参与文件名：拒绝空值与路径分隔符，防畸形 ID 逃逸目录。

## 5. 生命周期联动

| 事件 | 动作 |
|---|---|
| `deleteSession` 成功 | 删缓存文件（失败不删，保留无害） |
| SSE 远端删除 `_onSessionDeleted` | 删缓存文件（不走 deleteSession，漏了会留孤儿文件） |
| 换服务器（健康检查通过且 URL 变化） | `clearAll()`，防 A 服务器缓存被 B 服务器同名 sessionId 误命中 |
| 切项目 | **不**清缓存（sessionId 全局唯一，按文件隔离已足够） |
| 本地文件变更 `_onFileChanged` | 失效对应 worktree（或全量）的目录树缓存，保证文件抽屉刷新一致 |

## 6. 测试与验证

- `test/utils/session_cache_store_test.dart`：store 读写往返、覆盖写、原子写无 tmp 残留、删除、clearAll、损坏/版本不符 → null、空列表清理旧快照、路径分隔符拒绝、LRU 淘汰、残留 `.tmp` 清理。
- `SessionController.normalizeServerMessages` 单测：newest-first 翻转、非聊天事件过滤、往返一致性。
- `test/controllers/cache_optimizations_test.dart`：目录缓存前缀隔离与失效、二进制缓存 LRU、`revertMessageID` 恢复与重置。
- 控制器级 SWR 双阶段流转真机清单：
  1. 冷启动打开 100+ 条历史会话：首帧 < 100ms 渲染缓存，网络返回后无缝对齐；
  2. 打开会话后 2 秒内立即发送 → 网络快照返回不得冲掉乐观消息/流式内容（4.2 守卫）；
  3. 页签快速切换 + 中途切项目 → 无错位/污染；
  4. 本端 + 他端删除会话 → 缓存文件消失；
  5. 断网打开有缓存会话 → 秒开缓存、GET 失败静默（`historyLoadFailed=true`），切回页签自动重试网络；恢复连接后强刷对齐；
  6. 断网打开无缓存会话 → 走"加载失败可重试" UI，点重试正常。

## 7. 已知取舍与未做事项

- **写放大**：每回合收尾全量重写会话 JSON（大会话几 MB）。compute + 串行队列已规避卡顿，LRU 封顶磁盘；增量写复杂度高，v1 不做。
- **Android auto-backup 未排除**：缓存为明文聊天记录，manifest 未配置备份规则会进云端备份。待确认 support 目录在 Android 的映射路径后补 `fullBackupContent`/`dataExtractionRules` 排除 `session_cache/`。
- **为什么不放 Dio 拦截器**：拦截器无法感知 `isGenerating`/流式通道状态，会冲掉正在生成的流式内容；两阶段 UI 通知也需要业务层感知（详见 `loadMessages` 内注释）。
