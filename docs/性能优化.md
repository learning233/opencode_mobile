## A. 流式渲染链（最高优先级）

一条完整的重建风暴链：**delta flush → 整 messages RxList 广播 → 所有可见气泡重建 → 流式气泡 markdown 全文重 parse → 非流式气泡重跑正则扫描**。前三环是根因，后两环是叠加放大。

### A1. 双层 Obx 订阅整个 messages RxList —— 根因

位置：`lib/pages/home/chat_view.dart:173-190`、`lib/widgets/message/message_bubble.dart:266-312`

外层整个 CustomScrollView 包在一个 Obx 里，且 `allMsgs.toList()` 全列表拷贝（`chat_view.dart:189`）：

```dart
return Obx(() {
  ...
  msgs = allMsgs.toList();
```

每条气泡自己的 Obx 也读了 `state.messages`（`isNotEmpty` / `.last` / `indexWhere` 都是读操作，会注册依赖）：

```dart
final allMsgs = state?.messages ?? const <MessageModel>[];
final isLastMsg = allMsgs.isNotEmpty && allMsgs.last.id == message.id;
final msgIdx = allMsgs.indexWhere((m) => m.id == message.id);
final turnUserMsgId = _findTurnUserMessageId(allMsgs, msgIdx);
```

而 `_applyPartDelta`（`lib/controllers/session_controller.dart:3055-3083`）每次 flush（80ms）都 `state.messages[msgIdx] = MessageModel(...)` 整条替换 → RxList 广播给**所有**订阅者。

影响：流式期间每 80ms，**所有可见气泡（不只流式那条）**完整重建；每条还要做 O(n) 的 `indexWhere`、O(回合长度) 的 `_findTurnUserMessageId` 和 `_collectTurnDiffs` 扫描；外层再做一次全列表 `toList()` 拷贝 + 整棵 CustomScrollView 重建。另外 `message_bubble.dart:272` 每次重建还拷贝一次可见性 Map（`Map<String, bool>.from(Global.cardVisibilityRx)`），`message_bubble.dart:330-333` 每次重建都新建一层 `MediaQuery(copyWith(textScaler:...))` 使其下所有依赖者失效。

修复建议：
- 流式 delta 改走细粒度通道：为流式中的消息建单独的 `RxString`/`ValueNotifier<String>`（key 为 part.id），只有流式气泡订阅它；气泡 Obx 不再读 `state.messages` 整体（`isLastMsg`/`msgIdx`/回合信息由列表层算好传入）。
- `isGenerating` 单独订阅（已是独立 Rx），不与 messages 绑定。
- 卡片可见性 Map 拷贝只在值变化时做；`MediaQuery` 层只在字体缩放真正变化时重建。

### A2. 流式 markdown 每 80ms 全量重 parse

位置：`lib/widgets/message/markdown_view.dart:57-59`

```dart
return MarkdownBody(data: content, selectable: true, ...);
```

flutter_markdown_plus 的 `MarkdownWidget` 在 `didUpdateWidget` 中只要 `data` **或 `styleSheet`** 与旧值不等（均按实例比较）就全量重 parse（flutter_markdown_plus-1.0.12 `lib/src/widget.dart:364-370`）。流式时 content 每 80ms 变一次 → 单次 O(全文长度)，整条消息累计 **O(n²)**，且 parse + layout 都在主线程。更隐蔽的是：`MarkdownView` 每次 build 都新建 `MarkdownStyleSheet`（`markdown_view.dart:61-110`），即使内容没变，任何一次重建也会因 styleSheet 实例不等而触发全量重 parse。滚出屏幕 Sliver 销毁 State、滚回来再 parse 一遍，没有跨生命周期的缓存层。

正面点：代码块高亮已有 per-State 缓存（`markdown_view.dart:472-479`）且流式期间禁用（`markdown_view.dart:167` `highlightEnabled: !isStreaming`）。

修复建议：
- 快赢：`MarkdownStyleSheet` 按 isDark 记忆化（同一主题复用同一实例），使内容未变的重建不再触发 parse（一行级别的改动）。
- 对已完成消息按（message id + content 签名）缓存 parse 结果（LRU，如 64 条）。
- 流式消息可改为「仅重渲染追加段落」的增量方案，或降低流式期间的刷新频率（如 150-200ms），配合 A1 后只有一条气泡受影响，成本可接受。

### A3. ToolCallDetector 每次 rebuild 全文跑 18 个正则

位置：`lib/widgets/message/message_part.dart:38-42`、`lib/utils/tool_call_detector.dart:52-70`

```dart
text = text.replaceAll(RegExp(r'</?thinking>', caseSensitive: false), '');
final info = !isStreaming ? ToolCallDetector.detect(text) : null;
```

每次 build 新建 `</?thinking>` 的 RegExp（`_toolPatterns` 本身已预编译，`tool_call_detector.dart:44-51`）；`ToolCallDetector.detect` 先 `_stripCode` 全文按行 split/join，再对 18 个预编译正则逐个 `firstMatch` 全文扫描（命中即停，最坏 18 次全文扫描）。配合 A1，流式期间**所有可见的非流式文本气泡**每 80ms 都重跑这套扫描，O(可见气泡 × 文本长度 × 标签数)。

修复建议：detect 结果按（part.id + 文本长度/哈希）缓存（part 文本完成后不再变，天然可缓存）；`</?thinking>` 的 RegExp 提为 static const。A1 落地后非流式气泡不再被流式触发重建，此项压力自然大幅下降，但滚动重建时仍会跑，缓存仍有价值。

### A4. 双重 SelectionArea

位置：`lib/pages/home/chat_view.dart:153-160`、`lib/widgets/message/markdown_view.dart:57-59`

列表层每个 item 包 `SelectionArea`，而 `MarkdownBody(selectable: true)` 内部又建一层 selection 机制——同一段文本两套选择系统，长消息开销明显。

修复建议：二选一。保留外层 `SelectionArea`（可覆盖图片/工具卡片等非 markdown 内容），`MarkdownBody` 改 `selectable: false`；或反过来但需处理工具卡片的选中文本能力。改动小，注意回归验证选择/复制交互。

### A5. parts 无 per-part key

位置：`lib/widgets/message/message_bubble.dart:542-552`（`_buildPartColumns`）

消息只有外层 `ValueKey('msg_...')`，Column 内的 `MarkdownView` / `MessagePartWidget` 无 key。流式新增一个 part 时后续 children 按索引匹配 → 下游 Markdown State 被误复用，触发额外全量 re-parse。

修复建议：每个 part 加 `ValueKey('part_${part.id}')`。一行改动，收益稳定。

### A6. 流式结束瞬间代码块高亮同步执行

位置：`lib/widgets/message/markdown_view.dart:112`、`472-513`

流式结束瞬间 `isStreaming` 翻转，消息里**所有**代码块在主线程同步执行 `highlight()`，大代码块会卡一帧。

修复建议：高亮移到 isolate（highlight 库需支持），或对超过阈值（如 500 行）的代码块延迟分帧执行/先渲染纯文本再替换。

### A7. 次要项

| 项 | 位置 | 说明与建议 |
|---|---|---|
| TextShimmer 每帧逐字符分配 | `lib/widgets/message/text_shimmer.dart:80-98` | AnimatedBuilder 每帧为每个字符 `copyWith`+`withValues` 生成新 TextSpan 列表，reasoning 期间 60fps 常驻。改 `ShaderMask`/`FadeTransition` 等无逐字符分配方案 |

## B. 启动速度

### B1. main 三步串行阻塞首帧

位置：`lib/main.dart:6-11`、`lib/init.dart:58-69`

```dart
await AppLogger.init();
await Global.init();
runApp(const OpenCodeApp());
```

- `AppLogger.init`（`lib/utils/app_logger.dart:46-79`）：path_provider 平台通道 + 目录 IO，与语音、prefs 无依赖，可与 `Global.init` 并行或延后首帧后。
- `Global.init` 内 `await _initRust()`：`RustLib.init` dlopen 原生库 + FRB 注册，是启动链最重的单步；代码注释已明确「初始化失败不阻塞启动：仅语音降级」——既然可降级，不必阻塞首帧，可 `unawaited`，语音入口处再 await。
- 真正必须阻塞首帧的只有 `SharedPreferences.getInstance()`（主题/语言）。

修复建议：`Future.wait([prefs, logger])` + RustLib 延后/并行；语音入口（`VoiceInputService.initialize`）加一次性 await 兜底。改动小，白屏时间直接缩短一个「native 库加载 + 目录 IO」的耗时。

### B2. splash 后请求串行瀑布（经复核暂不实施）

位置：`lib/pages/splash_page.dart:135-145`、`lib/controllers/project_controller.dart:56-59`

`refreshAfterConnect()` 里 `fetchProjects` await 完成后才经 `selectProject → onProjectChanged` 发出会话/模型请求；而 `/project`、`/session`、`/config/providers` 三者互相无依赖。已有代际去重保护（`session_controller.dart:192-208`），并行化不会引起重复拉取。

**评估结论（2026-08-30，实施第一批时复核）：暂不实施。** 实际约束比预估强：
- `fetchSessions` 是目录作用域请求（拦截器按 `activeDirectory` 附加 `directory` 参数），必须等 `selectProject` 完成——这是真数据依赖，省不掉。
- 模型列表虽是全局端点（`fetchModels` 带 `skipDirectory: true`），但预取会在 `onProjectChanged` 递增 `_sessionFetchSeq` 后被代际守卫（`:590`、`:602`）整体丢弃并重新发起——预取只是把同一请求发两遍，省不了 RTT。
- 要真正省掉这 1 个 RTT 需要改写代际守卫语义（让全局端点豁免代际），属于正确性敏感改动，不符合「快赢」定位。收益仅冷启动 1 个 RTT，不值得冒这个险。

## C. 语音链路

### C1. 每次开始录音整读 27MB 资产

位置：`lib/services/voice_input_service.dart:392-409`（`_copyAssetIfNeeded`），调用链 `startListening` → `_prepareAssetPaths`（:485、:411-435），已人工核实

```dart
final byteData = await rootBundle.load(assetPath);   // 无条件全量加载
final expectedLen = byteData.lengthInBytes;
```

每次 `startListening` 都依次校验 `tokens.txt`（316KB）、`assets/vad_stream.onnx`（2.3MB）、`onnx/libonnxruntime.so`（**27MB**）——happy path（文件已存在且长度一致）下 27MB 仍被完整读入 ByteData 再丢弃，纯浪费的 asset 解压 IO + 内存分配 + GC 压力，直接加长「点麦克风→出声」延迟。

修复建议：从 `AssetManifest` 取资产期望长度做比对（零加载）；或加 `static bool _assetsVerified` 每进程只校验一次。注意保留注释中说明的设计意图：防止历史拷贝被中途杀死的截断文件（长度比对正是为此，不能去掉校验本身）。

### C2. stopListening 最长 5s 挂在手势路径

位置：`lib/services/voice_input_service.dart:641-644`（超时常量在 :643）、`lib/controllers/voice_input_controller.dart:385`

```dart
await done.future.timeout(const Duration(seconds: 5), onTimeout: () {});
```

长按松开发送要等冲刷完成才发文本；正常几百 ms，但 worker 异常时顶到 5s 的 UI 卡死感。`startListening` 也先 `await stopListening()` + 50ms delay（:482-483）。

修复建议：代码注释已说明 1s 在低端机/长句的 SenseVoice 冲刷下不够、5s 是刻意放宽——单纯调小超时会丢句尾。方向应是「发送最后一句」改回调驱动（onResult 送齐即发，不等满超时），或按实测自适应超时。保留冲刷本身（保句尾是设计必要）。

### C3. ASR 事件热路径 debugPrint

位置：`lib/services/voice_input_service.dart:513`（listen 回调从 :511 起）

每个 partial/final 转写事件都做字符串插值 + debugPrint（release 下 debugPrint 仍走 throttled print，不是 no-op），payload 是整段识别 JSON。包 `if (kDebugMode)`。

### C4. 每次录音重建 Rust 转写会话（长期项）

位置：`lib/services/voice_input_service.dart:495-508`

每次 `startListening` 都重新传模型路径建流（`runOnlineTranscription`），API 形态决定每次停-起都在 Rust 侧重建 worker/推理会话（模型是 ~230MB 的 q8 SenseVoice）。改进方向：暴露持久会话 + start/stop 分离，需要动 `rust/src/api/*.rs` 并按 AGENTS.md 重新生成桥接代码。列为长期项。

## D. 网络 / SSE / 重连

### D1. 重连成功后「全量风暴」

位置：`lib/controllers/session_controller.dart:2377-2395`（`_refreshAfterReconnect`）

每次 SSE 重连成功：全量 `fetchSessions` + `_restorePendingPermissions` + **每个打开页签** `loadMessages(force: true)` 全量 + 文件目录缓存全失效 + `invalidateAllFileContent()` 已打开文件全部重拉。移动网络抖动频繁时，一次断线 = N+2 个全量请求 + 所有已打开文件重新下载。

修复建议：只强刷**当前激活页签**，其余页签标脏（重置 `hasLoadedHistory`）懒加载；文件内容缓存同样按需失效。注意与 `_restorePendingPermissions`、todo 等正确性相关的补偿不能省，只省「体积大的全量重拉」。

### D2. SSE 大 payload 全部主 isolate 解码

位置：`lib/api/sse_client.dart:122-143`、`lib/api/models/event.dart:62`

所有 SSE 事件的 `jsonDecode` 都在 UI isolate；流式高峰每秒几十条事件，其中 `message.part.updated` 携带**全量累计 part JSON**（单事件成本随回复长度增长，累计 O(n²)）、`session.diff` 携带全量 diff 数组。全项目只有图片压缩走了 `Isolate.run`。

修复建议：大 payload 事件（按 raw 长度阈值判断，如 32KB）的 decode 移入 isolate（`compute`/`Isolate.run`，注意传输成本，可用 `Uint8List` 传原始字节）；小 delta 事件主线程直通。配合已有 80ms 合并，收益集中在长回复场景。

**评估结论（2026-08-30，第三批实施时复核）：暂不实施。** ① A1/A2 落地后渲染侧的放大已消除，剩余的主 isolate 解码在真实负载下是毫秒级（64KB ≈ 1ms）；② 阈值门控 `Isolate.run` 每次调用有 1-2ms 的 spawn + 传输固定开销，对 <500KB 的事件是净负收益；③ 真正的收益需要常驻解析 isolate（SendPort 双向通道 + 生命周期管理），工程量与收益不匹配。若未来实测流式高峰仍挤压 UI 线程，再立项常驻解析 isolate。

### D3. loadMessages 全量拉取 + raw 双份内存

位置：`lib/controllers/session_controller.dart:1214-1247`、`lib/api/models/message.dart:423-481`

`GET /session/:id/message` 一次性返回全部历史（服务端不支持分页，SSE 也不补发——此为服务端约束，客户端只能缓解）；`MessageModel.fromJson` 对 `info`、顶层 json、每个 part 各做一次 `Map.from` 拷贝（`message.dart:425、448、479`）→ 原始 JSON 与 `parts[].raw` 多份驻留，长会话内存放大明显。

修复建议：`raw` 只保留真正需要的字段（summary 判断等，见 `message_bubble.dart:286-289`）或改为按需保留；解析与建模可移 isolate（配合 D2）。改动需评估 raw 的所有消费点。

**评估结论（2026-08-30，第三批实施时复核）：不实施。** ① 实测代码确认各处 `Map.from` 都是浅拷贝——嵌套的字符串/`state` map 与原 JSON **共享引用**，实际多驻留的只是每消息/每 part 的 map 头，长会话合计约几百 KB，远低于勘察报告的「明显放大」估计；② 收敛 `raw` 需要动所有消费点（compaction summary 判断、`_onMessageUpdated` 的 summary 合并、fork、`toJson` 往返等），回归风险大于收益；③ HTTP JSON 解码已由 dio 5 默认 `BackgroundTransformer` 在后台 isolate 执行（pubspec 锁 dio ^5.9.2），主线程只剩 `MessageModel.fromJson` 建模循环，长会话也是毫秒级。

### D4. PTY 多终端恢复串行 attach

位置：`lib/controllers/pty_controller.dart:227-254`

每个 PTY 恢复 = 1 次 ticket POST（await）+ WS 握手（await），逐个串行，N 个终端总时长线性叠加。attach 之间无依赖，可并行（如 `Future.wait`）。注意循环内的 `seq != _fetchSeq` 幽灵会话防护（:228、:241-250）与串行 attach 时序耦合，并行化需保持该代际语义（如并行发起、完成后再按 seq 统一清理），并保证单个失败不影响其余。
