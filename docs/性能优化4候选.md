## E. 工具流式热路径（延续 A 系列未完成链路）

A1 修复后的现状：文本 delta 走 `streamingPartText` 细粒度通道，流式文本气泡只局部重建。但**工具 part 的更新路径没有对等改造**：每次 `part.updated`（bash 输出分块、tool 状态/元数据变化）仍整条替换 `state.messages`，把 A1 之前的风暴按服务端 part.updated 频率重放一遍。

### E1. 工具 part 更新仍整列表广播 —— 剩余根因

位置：`lib/controllers/session_controller.dart:3212-3230`（`_applyPartDelta` 非 text 分支）、`:3402-3445`（`_upsertPartInState` 全量更新）

`_applyPartDelta` 中 `item.field == 'text'` 已走细粒度通道，但注意两点：

- text 分支里 `rx.value += item.delta` 之后，`if (currentText.isNotEmpty) return true;` —— 只有「列表里已有内容」才提前返回，**首个 delta 仍落入下方整列表替换**（有意为之，驱动 showThinking → 气泡切换，但后续同 part 的 text flush 因 currentText 非空会 return，不再重复广播）；
- 非 text 字段（`field` 取自 `event.properties['field']`）每次 80ms flush 无条件走整列表替换：

```dart
state.messages[msgIdx] = MessageModel(...);  // :3223
```

`_upsertPartInState` 对每次全量 part.updated 同样整条替换。

列表一变的连锁（`lib/pages/home/chat_view.dart:181-198`）：外层 Obx 读 `allMsgs.toList()`（:197）+ `indexWhere`（:192）+ `lastIndexWhere`（:202）→ 整棵 CustomScrollView 及全部可见 item 重建；`MessageBubble` 以新实例下发（:161）→ 每个可见气泡 Obx builder 全部重跑 → 下发到各 tool 卡片触发 E2 的重复解析。

影响场景：agent 执行 bash/edit/read 密集的回合时，一次工具流式高峰等价于 A1 之前的文本流式风暴，频率取决于服务端 part.updated 频率而非固定 80ms。

修复建议：
- `_applyPartDelta` 非 text 分支与 `_upsertPartInState` 增加「内容无变化则跳过替换」守卫（raw 深相等或引用相等时直接 return），先消除 no-op 广播；
- 参照 text 通道做法，把 bash 输出等高频增长字段也建 per-part 通道（`streamingPartText` 的 key 已是 `partId\u0000field`，可直接扩展）；
- 配合 E2 的卡片级 memo（Part 不可变、整体替换实例，可在 Part 上挂解析缓存字段，与 `Part._toolOutputJson` 同模式）。

### E2. tool 卡片每次 build 重新解析原始数据

tool 卡片位于最热的通知消息列表里，E1 的每次列表广播、滚动重建、可见性切换都会触发；read/edit 是出现频率最高的工具，大输出时每次 build 都是 O(输出长度) 的解析/扫描。

| 位置 | 问题 |
|---|---|
| `lib/widgets/message/tool_cards/read_card.dart:52-54` | `_resolveRangeText` 在 offset/limit 缺失时每次 build 对整个 read 输出跑 `lineNumRe.allMatches(output).toList()` 并物化所有 Match（千行文件 = 千个 Match 对象/build），只为取 first/last |
| `lib/widgets/message/tool_cards/edit_card.dart:179`、`:461-511`、`:545-587`、`:699` | `_collectEntries` 每次 build 重跑：`_startLineFromPatch` 整 patch 按行 split + 逐行正则（:547）、`faithfulLines` 重新 split oldStr/newStr（:505-508）、`_countPatchChanges` 整 patch split（:699+） |
| `lib/widgets/message/tool_cards/glob_card.dart:21-23`、`grep_card.dart:21` | 每次 build 对整个输出 `output.split('\n')` 数行数 |
| `lib/widgets/message/tool_cards/question_card.dart:1222`、`:299-306` | build 内 `_getCompletedAnswers()` 每次 `jsonDecode(outputStr)` |
| `lib/widgets/message/tool_cards/bash_card.dart:12-14`、`read_card.dart:52`、`edit_card.dart:548/584` | RegExp 在函数体内每次新建 |

修复建议：解析结果按 part 实例 memo（Part 不可变、更新即整体替换新实例，与 `Part._toolOutputJson` 同模式）；`read_card` 用 `firstMatch` + 反向查找替代 `allMatches().toList()`；RegExp 提为顶层 `final`。

### E3. SessionStatusStack 与会话指示点：每次广播做 O(消息×parts) 扫描

- `lib/widgets/input_stack.dart:36-44`：主 Obx 读 `state.messages.length` 注册依赖后，每次重建调 `ctrl.pendingQuestionInTree()`（→ `session_controller.dart:91-104` `pendingQuestionPartFor` 全量扫描所有消息的所有 parts）和 `sessionIdWithPendingPermission()`（递归树扫描）；
- `lib/widgets/input_stack.dart:218-227`：`SessionDiffPanel` 同样 touch `messages.length`，并调 `state.effectiveSessionDiffs`（`lib/models/session_runtime_state.dart:116-193` —— 有签名缓存，但 `_effectiveDiffSignature()` 本身是 O(全部 assistant parts) 扫描，且 `sessionDiffs` 非空时直接放弃缓存返回）；
- `lib/widgets/input_stack.dart:543-546`：`PendingQuestionCard` 同样 touch messages + 全量扫描；
- `lib/pages/home/session_indicator.dart:107-109`：每个页签 dot `ever(messages)` 注册，触发时（非激活）跑 `requiresAction` 全消息×全 part 扫描（`session_runtime_state.dart:221-234`）。

影响场景：工具流式期间每次 part.updated → 这些 Obx 全部重建并各做一遍 O(n) 扫描，叠加在输入区正上方、与聊天区争抢帧预算。

修复建议：在 `SessionRuntimeState` 上维护惰性失效的「是否有 pending question / pending permission」布尔（在 `_processToolPart` / permission 事件处维护），Obx 只 touch 布尔；`effectiveSessionDiffs` 的签名改为 O(1) 版本号（parts 变更计数）。session_indicator 的 dot 同法收敛。

### E4. bash 底部弹窗流式期间 O(n²)

位置：`lib/widgets/message/tool_cards/bash_card.dart:10-15`（`stripAnsi` 内联创建 3 个 RegExp）+ `:201-207`、`:247/:268`

`_BashSheetBody` 的 Obx 订阅 messages，每次 build `stripAnsi(output)`：3 次 `replaceAll` 产生 3 个全量新串 + `SelectableText` 全量重排版。bash 输出流式增长时每次 part 更新都全量重算，长日志（100KB+）累计 O(n²)。

修复建议：3 个 RegExp 提为 static final；stripAnsi 结果按 part 实例缓存（同 E2 memo 模式）。

## F. 内存与资源治理

### F1. 平板布局冷启动即构建整个工具面板（含 WebView / 全部终端 / ReviewPage）

位置：`lib/pages/home/home_page.dart:442-461`；`lib/widgets/tablet/tablet_tool_panel.dart:115-123`

平板分支用 `Visibility(visible: toolVisible, maintainState: true, ...)` 包整个 `TabletToolPanel`。`maintainState: true` 在 `visible: false` 时子树仍会被 build 和 layout（Offstage），而面板内部是 `IndexedStack`（:115）——IndexedStack 会构建全部 4 个 children：Code 编辑器 PageView、`TerminalPanelBody`、`InAppBrowserView`（WebView）、`ReviewPage`。即使用户把面板设为隐藏（`_prefKeyVisible` 持久化，`tablet_tool_controller.dart:224`），冷启动首帧就全部实例化。

对比：手机布局已做惰性化（`home_page.dart:37,84-92` `_browserEverOpened`，冷启动不为 WebView 付费），平板没有对等策略。

修复建议：保持「切换不销毁」语义的前提下改为首次可见才挂载（如 `toolCtrl` 记录 `everVisible` 标志，首次 true 后不再卸载），或 IndexedStack 换成惰性懒建 + Offstage 保活。

### F2. 后台子会话 / 父会话 / 「清空页签」的历史驻留（普通页签关闭已释放）

位置：`lib/controllers/session_controller.dart:66`（`sessionRuntimeStates` Map）、`:1081-1104`（`closeSession` → `_releaseSessionState`）、`:702-708`（fetchSessions 重建父会话 childSessions）、`:1106-1111`（`clearAllOpenedSessions`）；`lib/models/session_runtime_state.dart:22,92,96`

**澄清（2026-08-31，回应「关闭对话后不清理内存吗」）：普通打开的页签关闭时是释放的**——`closeSession`（:1081）调 `_releaseSessionState`（:1096）→ `sessionRuntimeStates.remove(id)`（:1103），state 连同全量 messages 一起被 GC，重开页签时 `hasLoadedHistory` 随新状态重置、走正常懒加载；`deleteSession:1035`、SSE `session.deleted:2788`、vision 临时会话 :988 亦均有清理。本文档初稿「只在 onProjectChanged 与删会话时清理」的表述**不准确**，以本节为准。

真正的无淘汰驻留路径有四条：

1. **后台子会话（subtask）**：子会话不是页签，永远不会走 `closeSession`；回合结束后其全量历史（含工具调用消息与 raw 双份 JSON）驻留 map，直到切项目/删会话。这是「被 SSE 事件触及的会话」的主要构成。
2. **父会话关页签不释放**：`:1097` 对 `_parentSessionIds.containsKey(id)` 直接 return（注释：子会话状态由父会话的事件路径管理）——父会话 state（自身历史 + `messageSubtaskDiffs` 聚合）关页签后仍驻留；`childSessions` 树由 `fetchSessions:702-708` 重建，释放前需评估在跑子会话的 pendingQuestion/权限遍历依赖。
3. **挂起权限的会话跳过释放**：`:1101`，有意为之（asked 不重放，释放会让重开页签后的权限卡永久消失）；回复后关页签即正常释放。
4. **「清空所有页签」不释放 states**：`clearAllOpenedSessions`（:1106-1111，侧栏入口 `right_panel_content.dart:40`）只清 `openedSessionIds`/`activeSessionId`，map 原样保留。

另外：释放后若会话仍有事件到达（如后台生成中），`getOrCreateSessionState` 按未打开会话逻辑重建空壳 state（`:1092-1095` 注释）——空壳体量小，但生成中会重新积累流式消息。

对照：磁盘侧 `SessionCacheStore` 有 200 文件/64MB 双上限（`session_cache_store.dart:31-32`），内存侧无对等预算；`性能优化.md` D3 只评估了 raw 双份内存（不实施）。

修复建议（2026-08-31 定版，按用户拍板两条实施）：

**① 关闭父会话 → 级联清理子会话内容**：`_releaseSessionState:1097` 的父会话分支不再直接 return，改为级联处理——

- 父会话 state **保留轻量外壳**（`childSessions` 树是 `pendingQuestionInTree:475-486`/权限遍历的依赖，`fetchSessions:702-708` 重建前的窗口不能为空），但清掉 `messages`/`streamingPartText`/`turnDiffCache`/`messageSubtaskDiffs`/`fetchedMessageDiffs`，并**重置 `hasLoadedHistory=false`**（否则重开页签时 `:1234` 的守卫会挡住重拉，聊天区空白且待答问题卡丢失）；
- 其 `childSessions` 的子会话 state 逐个 `_releaseSessionState` 整个 remove（多层嵌套同规则递归），重开时经懒加载/事件路径回填，与普通页签释放同理。

**② `clearAllOpenedSessions` 全量释放**：遍历 `sessionRuntimeStates`（含不在 `openedSessionIds` 里的后台子会话）逐个释放——父会话走 ① 的级联逻辑，普通/子会话走现有 `_releaseSessionState`；释放集合统一调一次 `_discardPendingPartDeltas(sessionIds: ...)`。

**守卫**：沿用现有唯一约束 `pendingPermission.value != null` 跳过（:1098-1100，asked 不重放，防权限卡永久丢失）；生成中的会话不额外设守卫——与现有普通页签释放语义一致（`:1092-1095` 注释：释放后事件到达由 `getOrCreateSessionState` 重建空壳，重开时 loadMessages 全量纠正）。

预期收益：关闭/清空后内存即时回落；后台子会话历史不再累积到切项目。

### F3. image_cache 只有时间清理，无总量上限

位置：`lib/utils/image_cache.dart:52-68`

## H. 网络与数据层

### H1. loadMessages 无「同一会话在途去重」，会产生并发的重复全量历史 GET

位置：`lib/controllers/session_controller.dart:1234-1243`（守卫）、`:1242-1243`（入口即把 `hasLoadedHistory`/`historyLoadFailed` 重置为 false）、`:771-775`（`_restoreOpenedSessions` 对每个恢复页签 `unawaited(loadMessages(id))` 预取）、`:1065`/`:1078`（`selectSession` 每次切换都调 `loadMessages`）、`:2490`（SSE 重连 `force: true` 强刷活跃页签）、`:1858`/`:3331`/`:3361`（其它 force 路径）

守卫只判断「是否已加载完成」，而 `loadMessages` 一进入就把 `hasLoadedHistory` 置回 false，之后才 `await` 网络。因此在途期间同会话的第二次调用必然穿过守卫再发一次 GET；`force: true` 则完全绕过守卫。没有按 sessionId 的在途 Future 表，也没有 CancelToken 去取消被取代的旧请求。

影响场景（`会话缓存.md` 实测全量历史 GET 约 4.4s，窗口很大）：
- 冷启动恢复多页签：预取在途时用户滑到该页签，`selectSession` 再发一次；
- 移动网抖动：SSE 以 1s/2s 快速退避连续重连成功，每次 `_refreshAfterReconnect`（:2482-2510）都对活跃页签 `force: true` 全量拉取，4.4s 窗口内可叠 2-3 个并发大响应；旧响应后到还会 `assignAll` 覆盖较新数据（seq 守卫只防「切项目」，不防同项目内乱序）。

注 1：`session_controller.dart:767-770` 的注释声称「loadMessages' hasLoadedHistory guard dedupes with the selectSession call」，实际该去重仅在首个请求**完成后**（`hasLoadedHistory=true`）才成立，在途窗口内不成立——预取 + 立即切页签正是注释以为已防住的场景。
注 2：`性能优化.md`「已确认良好」一节称 loadMessages 有「代际去重」，实际代际只防切项目——该表述与代码不符（见 J 系列）。

修复建议：加 `Map<String, Future<void>> _messageLoadInFlight`（同会话在途直接返回同一 Future；force 到来时可选择取消旧 CancelToken 再发）。

### H2. 图片/音频查看器下载路径：多 MB base64 的正则清洗 + `base64Decode` 全在主 isolate

位置：`lib/widgets/multi_view/image_viewer.dart:106-108`、`lib/widgets/multi_view/audio_player_view.dart:111-113`（两处代码逐行相同，取值逻辑在各自上方 ~15 行）

```dart
base64Content = data['content']?.toString() ?? '';
final Uint8List bytes = base64Decode(base64Content.replaceAll(RegExp(r'\s+'), ''));
```

JSON 解码已由 dio 的 `BackgroundTransformer` 承担（已核实 pubspec.lock 解析为 dio-5.11.0，其 `background_transformer.dart` 对 **≥50KB** 的响应体走 `compute(jsonDecode, text)` 进后台 isolate，<50KB 仍在主线程解析——查看器场景响应体远超 50KB，故 JSON 解码不占主线程），但随后的 `replaceAll(RegExp(...))`（对 ~6.7MB 字符串跑正则）和 `base64Decode`（~1.37× 文件大小的分配）都在 UI 线程同步执行。对比发送侧——压缩编码已全部进 `Isolate.run`（`session_controller.dart:1694`、`:928`），接收侧漏了。

修复建议：整段（replace + decode）放进 `Isolate.run`/`compute`。注：`代码审查.md` 链路 7-10 已登记「大文件无防护 / base64 峰值 1.37×」同族问题，本条是查看器下载路径的具体站点。

### H3. SessionCacheStore.load 的 UTF-8 解码留在主 isolate + _dir() 重复平台通道

- `lib/utils/session_cache_store.dart:68`：`await compute(jsonDecode, await file.readAsString())` —— `compute` 只把 `jsonDecode` 挪出主线程；`readAsString()` 内部的 `utf8.decode(bytes)` 仍在主 isolate 同步执行。大会话缓存单文件可到数 MB，bytes→String 在主线程约 10-25ms，SWR 秒开路径本意不卡帧，数 MB 命中时首帧前仍有一次主线程大字符串解码。建议 `readAsBytes()` 后把 `Uint8List` 传进一个 `compute`，在 isolate 内一并做 `utf8.decode + jsonDecode`。
- `lib/utils/session_cache_store.dart:40-49`：每次 `load/save/delete/clearAll` 都 `await getApplicationSupportDirectory()`（platform channel）+ `dir.create(recursive: true)`（syscall）。`_restoreOpenedSessions` 一次预取 N 个页签重复 N 次。建议首次解析后缓存 `Directory` 实例，`create` 仅首次执行（`_baseDir` 注入测试路径不受影响）。

### H4. post/patch/put/delete 不支持 CancelToken（代码审查.md 已登记，列为遗留项）

位置：`lib/api/opencode_client.dart:140-185`（四个方法签名均无 `cancelToken` 参数，对照 `:127` get 有）；GET 侧仅 `file_search_controller.dart:71-106` 在用，VCS（`vcs_controller.dart:96-138`）、`loadDirectory`（`project_controller.dart:288`）、文件内容/图片查看器、`loadMessages`（`session_controller.dart:1266`）均未取消。

影响场景：切项目时（`_sessionFetchSeq++` 只是丢弃响应）在途的大响应继续下载占带宽。建议为四个写方法补 `CancelToken` 参数；至少给 `loadMessages` 与文件族 GET 接上取消（配合 H1）。

### H5. loadDirectory 无在途去重

位置：`lib/controllers/project_controller.dart:282-292`：缓存 miss 后直接发 GET，两个 widget 并发请求同一目录（文件树 + code_viewer 同路径）会各发一次。缓解因素：`lib/widgets/left_drawer/file_tree_view.dart:137-138` 有 300ms 防抖、SSE file 变化只失效不主动拉，碰撞窗口窄。建议与 H1 同法缓存在途 Future。
