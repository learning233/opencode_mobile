## 2. 修复记录

### 2.1 P2 · SWR 缓存快照缺流式内容（parts 与 raw 分叉）

`MessageModel.raw` 与解析后的 `parts` 是两份独立数据，构造器不回写。而本轮引入的三条路径都只更新 `parts`（甚至只进 per-part 通道）：

- 文本 delta 的 80ms flush 走 `streamingPartText` 通道，仅首个 delta 写一次列表；
- `_finalizeStreamingText` 把通道累计值写回解析后 part 的 raw；
- 工具状态标记（abort/skipped/replied）同样只替换 part。

但 `_persistSessionCacheSnapshot` 落盘取的是 `m.raw`——其 parts 键停留在**最后一次全量 message.updated** 的内容。结果：Sync-on-Idle 存的快照缺失流式文本，冷启动（断网/重装）读缓存渲染出截断回复，虽然下次 revalidate 能自愈，但「秒开缓存」展示的正是这份残缺数据。

修复：新增 `SessionController.messageWithSyncedParts(message, parts)`（`session_controller.dart`）——把当前 parts 回写进 raw **副本**（不污染原 map），兼容 legacy `parts` 与 v2 `info.content` 两种形状（写进全部现存列表键；均无列表键且 parts 非空时补写 `parts`），并补齐 `id`/`sessionID` 供 `fromJson` 还原身份（修复 `_upsertPartInState` 合成外壳消息——raw 原本只有 `{'role':'assistant'}`，落盘重读后 id 变空、parts 丢失）。8 处整条消息替换点（abort 标记 / 首个 delta 落列表 / finalize / part 删除 / part upsert 两分支 / question resolved / stale question skipped）统一接入；落盘处再做一次兜底同步，防未来某个变更点漏调。

回归测试：`test/controllers/message_parts_sync_test.dart`（legacy/v2 往返一致、原 raw 不被污染、合成消息身份补齐）。

### 2.2 P2 · 重连强刷后流式文本冻结（通道孤儿引用）

`_StreamingTextMarkdownState`（`message_part.dart`）把通道 `RxString` 缓存进 State，`didUpdateWidget` 只在 part.id/sessionId 变化时重挂。而重连强刷路径（`loadMessages(force:true)` → `streamingPartText.clear()` + `assignAll`）清空通道 Map 后，Element 复用使 State 仍持有已移除的旧 RxString——后续 delta 经 `putIfAbsent` 写进 Map 里新建的通道，气泡冻结在断线前内容，直到回合结束。

修复：`didUpdateWidget` 增加对账——Map 已有新通道则改挂；通道缺失**且回合仍在生成**则按列表当前文本重建（与 flush 侧 putIfAbsent 同种子）；通道缺失且已收尾则丢弃引用改读列表文本。不重建收尾后的通道是刻意的：`_persistSessionCacheSnapshot` 与 SWR revalidate 守卫都以 `streamingPartText.isNotEmpty` 判「流式未收尾」，widget 侧无中生有会造出假状态跳过落盘/对齐。

### 2.3 P2 · 发送失败回填写已卸载的输入框

`_submitMessage`（`prompt_input.dart`）`await sendPrompt` 之后无 `mounted` 守卫：POST 窗口内关闭页签 → PromptInput dispose → POST 失败回填写已 dispose 的 controller（debug 抛未捕获异步异常、release 静默丢输入）。修复：`mounted` 守卫包住输入框回填；附件仍属会话运行时状态、照常回填。顺带移除无条件 `_hasText = true`（纯附件发送失败时会把空文本标成有字），该标志由 controller listener 按 trimmed 文本维护，程序化赋值自然触发。

### 2.4 P3 · loadMessages 票据 finally 竞态

`_loadMessagesImpl` 的 `finally` 只要 `seq` 未变就把 `hasLoadedHistory=true`：被 force 取代的旧请求（CancelToken 取消路径）会在取代者飞行期间置 true，空会话 UI 在「正在加载」与「开始对话」间闪跳最长一个全量 GET 的时长；同理迟到错误会把 `historyLoadFailed` 压到取代者头上。修复：catch/finally 增加 `_messageLoadTickets[sessionId] == ticket` 守卫（被取代即放弃收尾，取代者自身 finally 负责终结加载态；票据只在真实新加载时递增，在途去重复用 Future 不 bump，语义闭环）。

### 2.5 P3 · closeTerminal 用过期索引改列表

`pty_controller.closeTerminal` 先 DELETE 远端（最长 5s 超时）再删本地，但 `idx`/`filteredIdx` 在 await 之前计算。await 期间 `fetchSessions` 的 stale 清理（DELETE 成功本身就会促成——下次列表刷新把该会话判为已删并 dispose+移除）与并行 attach 代际清理会并发修改 `sessions`：旧代码 `removeAt(idx)` 会删错相邻会话或越界抛 RangeError（closeTerminal 为 fire-and-forget 调用，异常静默），且对已被清理的会话二次 `dispose()`（FocusNode/TerminalController 断言）。修复：await 后按对象身份复查（`sessions.contains(session)`，不在则交由 fetchSessions 既有的悬空 activePtyId 纠正）；激活页签回退目标改为 await 前按对象引用捕获相邻存活项、await 后重解析。

### 2.6 P3 · VCS 迟到旧失败清空新结果

`vcs_controller` 的 seq 守卫只挂在响应成功路径：`fetchVcsStatus` 的 catch（`error.value` + `statusFiles.clear()`）、`fetchVcsInfo` 的 404 分支（清 branch/defaultBranch）均无守卫——被 force 取代的旧请求 60s 超时失败后，会清空新请求刚写入的数据；`refreshAll` 的 finally 无条件 `isLoading=false` 会提前关掉新刷新的在途 loading。修复：三处补 `requestSeq != _refreshSeq → return`（404/400 的「非 git 仓库」清空一并守卫，新请求若同样 404 会自行写入该状态）；finally 按代际收尾（与 `pty_controller.fetchSessions` 同口径）。

### 2.7 P3 · 语音停止冲刷期自动发送误扫全文

`stopSingleTap` 先 `_lockFlushTarget()` 再 `_setTarget(null)`，而 `_setTarget` 会把 `_voiceStartLen` 归零；≤5s 冲刷窗口内送达的句尾 final 走自动发送分支时读到 0，`_extractAutoSendText` 退化为从 0 起全文扫描——恰会命中用户手打的「，发送。」把旧文本连同句尾一起误发送（正是早前 P3 修复要防的场景，正常监听路径已防住、唯独停止冲刷路径退化）。修复：新增 `_flushStartLen` 与 `_flushLastLen` 同生命周期锁定，冲刷期匹配用锁定值。

### 2.8 P3 · 图片 provider 缓存键缺内容成分

`message_part.dart` 两条附件图片缓存（G3/A7）键不含内容：data: 键为 `messageID:partId`，file:// 键为路径。`didUpdateWidget` 的 URL 变化检测与文件被编辑（同路径内容变化）都会命中旧 provider 显示旧图。修复：data: 键追加 `url.hashCode`；file:// 先 `stat()` 再以 `路径:size:mtime毫秒` 为键（多一次 stat 换取编辑后重读，仍跳过 decode 的主要开销）。

### 2.9 P3 · 推理弹窗错过晚创建的通道

`_ReasoningSheetBody`（`reasoning_part.dart`）对通道纯读不建：若「全量 part.updated 先把文本写入列表、后续走 delta」，弹窗 build 时通道尚不存在、Obx 未订阅，后续 delta 只进新通道不通知弹窗，内容停到 finalize。修复：生成中按当前列表文本 putIfAbsent 惰性创建（与 flush 侧同种子，Obx 读 `state.isGenerating` 注册依赖，翻转即重建）；已收尾只读不建——不给已完成 part 造幽灵通道条目（理由同 2.2）。

### 2.10 P3 · 页签栏自动滚动一次性失败不再自愈

`file_page.dart` 与 `tablet_tool_panel.dart` 的 `_lastEnsuredTab` 去重：`ListView.builder` 懒构建下，目标页签在视口+cacheExtent 之外时 postFrame 里 `currentContext` 为 null，ensure 落空且去重标记已置位、不再重试——「打开文件自动滚到新页签」失效。修复：postFrame 内发现未 materialize 时重置 `_lastEnsuredTab`，待后续 rebuild 重试（页签 materialize 后即成功，不会与用户手动滚动打架——仍只在选中页签变化时触发）。

### 2.11 P3 · 页签 dot 创建即挂起不闪烁

### 2.12 P3 · 流式切分围栏配对不严

## 5. 回归关注点（真机清单）

1. **流式完整性**：长回复打字、流式中 abort/出错、流式中断网重连（修 2.2 的主场景）——气泡文本应持续增长、回合结束后无重复/缺尾；
2. **缓存往返**：发送带流式回复的会话 → 回合结束 → 杀进程冷启动 → 秒开缓存内容应与在线时一致（含最后一段文本、工具卡片终态）；删会话/他端删除后缓存文件消失；
3. **发送失败回填**：飞行模式发送 → 文本/图片/文件应回填输入区且发送按钮态正确；失败提示期间关闭页签不报错；
4. **终端**：关闭非激活/激活终端页签，相邻页签自动激活指向正确；DELETE 成功后立即触发 fetchSessions 的并发场景不再崩；
5. **VCS**：弱网下快速连续打开/刷新 Review 面板，无旧响应覆盖新数据、无 loading 卡死；
6. **语音自动发送**：开着口令发送，手打文本含「，发送。」→ 单点停止 → 冲刷句尾不应把旧文本发出；
7. **附件缩略图**：agent 编辑同路径图片文件后滚动往返，缩略图显示新内容；
8. **页签指示点**：后台页签收到提问/权限时光晕出现；创建时已挂起的后台页签光晕直接可见。

## 6. 追加复审（2026-09-05 · 外部报告两隐患核实）

针对外部报告的两条隐患逐行核实（触发链路均以终态代码验证，测试见 `test/controllers/session_cache_snapshot_guard_test.dart`）：

### 6.1 P1（已修）· 后台会话局部消息覆盖磁盘全量快照

**报告属实**。冷启动后未打开的会话收到另一端（Web/CLI/子智能体）回合的 SSE：`message.part.updated` 经 `getOrCreateSessionState` + `_upsertPartInState` 为其凭空建状态（`hasLoadedHistory=false`）并塞入本轮消息壳，`message.updated` 随后追加；回合收尾 `session.idle`/`session.error` → `_persistSessionCacheSnapshot` 保存分支**无 `hasLoadedHistory` 守卫**，把只含本轮片段的内存原子覆盖进磁盘，完整快照被截断。后果：离线冷启动只能看到最后一轮；联网时 SWR 秒开闪现截断内容、revalidate 后自愈（服务端仍是权威全量，非永久丢失）。

修复：保存分支加 `!hasLoadedHistory` 即 return（与删除分支对称的权威态语义——未加载态的内存一律视为局部/未知，快照留给下次全量 revalidate 落盘自愈）。另核实补充触发面：生成中打开页签时 `snapshotStale` 豁免赋值/落盘，同一收尾路径同样截断，本修复一并覆盖。保存分支刻意**不**卡 `historyLoadFailed`：SWR 回填 + 本端继续会话的场景内存完整，应照存。

### 6.2 P3（定案不修 + 保险带）· loadMessages 失败 finally 置 hasLoadedHistory=true 误删缓存

**报告的触发器属实、数据丢失后果不成立**。`finally` 确实在失败时置 `hasLoadedHistory=true`（语义应为"加载尝试已终结"，为空会话 UI 三态渲染服务），删除分支也确以该标志为条件；但 SWR 预读保证：磁盘有可读快照时 `loadMessages` 先把它填进内存再发 GET，网络失败时内存非空 → 删除分支不可达（走保存分支重落缓存内容）；删除分支可达时（load 返回 null：文件缺失/损坏/空）磁盘本无完整快照可丢，竞态窗口内 `hasLoadedHistory` 亦为 false。不修 `finally` 行为的原因：改语义需重构 chat_view 空会话三态 UI，实际危害已被 SWR 预读封死。保险带：删除分支追加 `!historyLoadFailed` 条件，显式表达"网络失败不构成删除授权"，防未来新路径踩雷。
